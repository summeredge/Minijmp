### Tk 生命周期根因

原两个 PI 用例单独/合并以及 PI 整文件都通过；
旧生产代码的诊断全量仍精确重现两个原 PI teardown error。
该轮新增一个创建 Frame 的列记忆测试，原 `.!frame200.!mtable` 顺延为 `.!frame201.!mtable`。

根因不是 PI reader 的 worker 或 poll：`Table.show()` 在父 Frame 注册 `<Configure>` → `self.resized`，
而部分 G21 测试只 `table.destroy()`，保留已 pack 的父 Frame。父 Frame 和 Tcl 注册命令继续持有已销毁表格。
后续 PI 窗口/布局更新触发该旧 Frame 的 Configure，错误通过当前 root 的异常处理器记在 PI fixture 收尾。

注册路径：`test_g21_plotter.make_viewer → table.show → parentframe.bind`。
回调路径：`resized → redrawVisible → Canvas.configure` → `TclError: invalid command name`。

三层证据：

1. 最小实验保留父 Frame、销毁表格、触发 Configure，稳定得到相同堆栈。
2. 新增回归在 OriginalTable、Table、MTable 上均拒绝旧实现：3 failed、3 passed。
3. 显示 session root，G21→PI 顺序组合记录注册/异常堆栈，37 passed、2 teardown errors，错误 ID 与原两项一致。

完整原始堆栈见 `tk-registration-trace.log`，顺序组合命令/日志见 `trace_order.py`、`order-trace.log`。
临时探针只记录运行时注册堆栈、显示 root，不修改源码、不替换业务行为或吞异常。
同一组合改用修复后副本，37 passed、0 errors；`tk-registration-after.log` 中没有 CALLBACK ERROR。

最小生产修复仅在 `code/pandastable_local/core_orig.py`：保存父 Frame 的 resize binding ID，
表格 `<Destroy>` 时用 ID 注销自己的绑定和 Tcl 命令；清理幂等，重复 show 先清理旧 ID。
其他订阅不被删除，不加吞异常或销毁后继续执行的兼容路径。
父容器销毁也会发送子组件 Destroy，因而不依赖 `WM_DELETE_WINDOW`。

没有修改 `dialog.py`、`qc_dialog.py`、`worksheets.py`、PI 导入实现或异步对话框。
PI cancel 已取消保存/poll ID，文本 viewer close 已取消滚动 idle；本轮证据不支持扩展重构这些模块。
